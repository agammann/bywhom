# ByWhom extension build notes

## Scope and data path

1. `manifest.json` declares Manifest V3, Chrome 116 minimum, a toolbar action, a service worker, and a bundled side panel. Permissions are `activeTab`, `scripting`, and `sidePanel`; there are no host patterns.
2. A toolbar click reaches `background.js`. It starts `chrome.scripting.executeScript()` and `chrome.sidePanel.open()` from that user gesture. A generation counter discards a capture result if a newer click, Clear, or tab change supersedes it. Tab update/activation/removal listeners only invalidate the currently displayed result; they do not capture page content.
3. `capture.js` runs once in the permitted tab's **main frame**. It returns a bounded object with page URL/title for context, selected text outside editable controls, candidate visible credit lines, `meta[name=author]`, `meta[property=article:author]`, `og:site_name`, `application-name`, and Article-family JSON-LD author/publisher names. Visible lines carry a location label and line number; metadata carries its field/JSON-LD location. Invalid structured data is skipped.
4. `credit-engine.mjs` parses only explicit English credit patterns. It keeps writer, host, and origin separate. The selected text is parsed as a credit only if the selected text itself contains a supported credit line; other current-page evidence is analyzed independently. Distinct claims are retained as a conflict. Metadata-only claims are labeled metadata, not promoted to verified visible credit. URL/title alone assign no role.
5. `panel.mjs` builds result and evidence nodes with DOM methods and `textContent`, keeping page-supplied strings out of HTML parsing. Evidence links are accepted only as HTTP(S) URLs and open with `noopener noreferrer`. Pasted text uses the same local parser but is never merged with an earlier page capture. An optional pasted URL appears only as unverified context.

The [Chrome `scripting` API](https://developer.chrome.com/docs/extensions/reference/api/scripting) supports this explicit injection; [`activeTab`](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) is the temporary page-access grant. [`sidePanel.open()` requires a user gesture and was introduced in Chrome 116](https://developer.chrome.com/docs/extensions/reference/api/sidePanel#open).

## Privacy and failure boundaries

- No automatic clipboard read, background article collection, account, paid API, remote script, web-wide origin search, or network fetch is part of the extension. The user may choose to follow a link found in a credit; the article site itself may make its normal network requests.
- The action rejects non-HTTP(S) pages for capture and shows a paste fallback if injection fails. It does not evade restricted schemes, paywalls, or site permissions.
- The page reader excludes inputs, forms, editable selections, hidden elements, and nonvisible elements from visible evidence. Capture is limited to 60,000 returned characters, 30,000 selection characters, 100 candidate visible lines, 24 author and 24 site metadata items, and 20 JSON-LD scripts. Long lines are omitted rather than shortened and misrepresented as exact credit evidence.
- Image/canvas text, closed or untraversed shadow DOM, cross-origin frames, and missing/unusual byline structures can be missed. Metadata can be stale or wrong. Distinct metadata and visible claims are shown together as a conflict; neither independently verifies the other.
- Credit results are held in memory and cleared on changed page/tab or Clear. Only the animation preference is saved via the side panel's `localStorage`. The detective is a bundled local image; CSS provides idle, investigating, and result states, a pause control, and `prefers-reduced-motion` behavior.

## What has been verified

- `tests/credit-engine.test.mjs`: **13/13 passing** in Node's built-in test runner. The cases cover WUSF inline credit and newsroom-affiliation normalization, The Conversation republication sentence, writer versus illustrator/editor, multiple and organization authors, conflicting writer/origin, metadata-only labeling, visible-versus-metadata conflicts, no URL/title inference, HTTP(S)/markup safety, and input bounds.
- `tests/background.test.cjs`: **5/5 passing** for action-only injection, navigation reset, restricted-page fallback, late-result suppression, and Clear. `tests/manifest.test.mjs`: **1/1 passing** for the narrow MV3 permission set.
- JavaScript syntax checks have passed for the extension scripts.
- `tests/capture-regression.cjs`: **passed** on a local article with related story cards. The current article's byline, illustrator role, and republication statement remain in the capture; unrelated related-card bylines do not.
- `tests/browser-smoke.cjs`: **11/11 passing** in an isolated headless Chromium profile with the unpacked extension. It evaluated the bundled `capture.js` on local fixtures, then delivered its captured state to the real bundled panel. This is a **panel/capture simulation**, not a toolbar click or an `activeTab` grant. Checks covered the narrow MV3 manifest; WUSF credit plus selection; evidence Enter/Escape/focus restoration; visible versus metadata conflict with both source labels; explicit Conversation origin and unknown NASA Page Editor; hidden bylines; inert hostile metadata evidence; paste, repeated submissions, and Clear; simulated stale state; 320 px and 390 px bounds; and no console/page errors, failed requests, or external requests. Screenshots were captured at both narrow widths.
- `tests/capture-fixtures.md` also records intended page-capture cases; entries outside the executed smoke test remain a test plan.
- `tests/action-gesture.cjs`: **6/6 passing** in a separate isolated Chromium profile. It invoked the actual MV3 action via browser-level CDP `Extensions.triggerAction` on a tab target, exercising `action.onClicked` and `chrome.scripting.executeScript` with the temporary `activeTab` grant. The WUSF line and selected text survived panel focus; a second action refreshed the selection; navigation invalidated the old capture and a new action read the new page; `chrome://settings` produced the paste fallback; and a real side-panel target opened. The run recorded zero console/page errors and external requests. This proves the browser action path through a **programmatically triggered extension action**, not a person's physical toolbar click in Chrome.
- [Public-article compatibility check](LIVE-PAGE-COMPATIBILITY.md): **3/3 pages returned HTTP 200 and extension `ready`** after a genuine action event in isolated Chromium. WUSF now credits Darius Tahir and WUSF while leaving origin unknown; KFF excludes related cards but retains a visible-writer versus metadata-author conflict; the South Carolina page shows Forest Agostinelli, a metadata-only host claim, and an explicit The Conversation republication credit. A second WUSF action captured a selected paragraph exactly. There were no extension-worker errors; WUSF and South Carolina emitted page-side diagnostics. The test recorded capture and engine analysis, not a visual side-panel assertion on those public pages.

The direct Node test commands are `node .\tests\credit-engine.test.mjs`, `node .\tests\background.test.cjs`, and `node .\tests\manifest.test.mjs`. The direct form passed on the restricted Windows test host; `node --test` may fail with process-spawning `EPERM` there. The browser commands are `node .\tests\capture-regression.cjs`, `node .\tests\browser-smoke.cjs`, and `node .\tests\action-gesture.cjs`. These harnesses need Playwright and Chromium test dependencies. They resolve Playwright from `node_modules`, module-path environment variables, or the active Node runtime, and use `PLAYWRIGHT_BROWSERS_PATH` or the sibling `.playwright-browsers-bywhom` cache when present. These are not installation prerequisites for the extension itself.

For a manual check after loading unpacked into an isolated profile: use a local article with a visible `By` line and a selected phrase, click the real toolbar button, inspect writer/host/origin and exact evidence, click again after selecting different text, navigate to another page, and check that stale results disappear. Try a restricted page to confirm the paste fallback, then test repeated paste submissions, Clear, Tab, Enter, Escape, and Pause animation. The user must choose whether to install in their own Chrome; no normal-browser installation was done in this build task.
